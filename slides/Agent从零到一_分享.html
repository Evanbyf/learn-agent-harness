开场 · 核心比喻

从这个画面，能推出博士生的三条天性

①

他不记得上一次

每次调用都是全新的开始。想让他“记得”，就得把以前的内容再塞一遍。

②

他碰不到任何东西

他只会写字。订会、发消息、建文档，都得有人照着纸条去做。

③

门缝塞得下的纸有上限

纸越厚越贵、越慢；太厚就塞不进去；塞太多，他还会看漏。

③ 建立在 ① 之上：每次都要把以前的内容重塞一遍，纸只会越来越厚，而一次塞得下的有限

后面所有的机制，都是为了对付这三条天性。

术语① 模型无状态 · ② 只输出文本 · ③ 上下文窗口
  • （2 分钟）请大家记住这三条，后面每讲一个机制，我都会指回来：这是在对付第几条。
  • ① 无状态：今天聊天产品看起来“记得”你，是因为每次都把历史重新发了一遍。
  • ② 只能输出文本：它没有手，所有“动作”都是别人替它做的。
  • ③ 上下文窗口：有上限，按长度计费，而且越长越容易“看漏”中间的内容。注意那条虚线：③ 是建立在 ① 之上的。因为每次都是全新开始、要把以前的内容重塞一遍，纸才会越来越厚；而一次能塞的又有限，塞多了要么塞不进去，要么注意力不够。

刚才那 4 圈，写成代码就是这么一段（Agent loop）

# 那叠纸：只增不减
messages = [{"role": "user", "content": "帮我约明天下午和产品组开个会…"}]

while True:
    resp = client.messages.create(          ① 把整叠纸塞进门
        system=SYSTEM_PROMPT,               # 岗位说明书
        tools=TOOLS,                        # 工具说明书
        messages=messages)                  # 全部历史，每次重发
    messages.append({"role": "assistant", "content": resp.content})

    if resp.stop_reason != "tool_use":      ② 他还要用工具吗？
        break                               # 不要了：答案交给用户

    results = []
    for block in resp.content:
        if block.type == "tool_use":
            out = run_tool(block.name, block.input)  ③ 门外照纸条去做
            results.append({"type": "tool_result",
                            "tool_use_id": block.id, "content": out})
    messages.append({"role": "user", "content": results})  # 写成新的一页

Agent 的心脏，
就这么大。

  1. ①把整叠纸塞进门：岗位说明书、说明书、全部历史
  2. ②看纸条：他还要用工具吗？不要了就结束
  3. ③门外照着纸条去做，结果写成新的一页，回到 ①

后面讲的所有东西，都是往这个循环上“挂”。循环本身，一行不改。

  • （2 分钟）看不懂代码没关系，盯住三个黄色标记。
  • 给开发同学：messages 只有两个追加点，assistant 回复一次、tool_result 一次。tool_result 以 user 角色回灌，用 tool_use_id 配对，所以并行调用不会张冠李戴。

工具 = 一份说明书 + 一双门外的手

加一个工具，只加两行

往工具列表里加一份说明书，往分发表里加一个处理函数。循环一行不改。

说明书决定他会不会用

做什么、什么时候用、参数、返回。说明书写不清，他就会选错工具、瞎猜参数。

失败也写成纸条递回去

“会议室已被占用”递回去，他会自己换个时间；直接报错崩掉，整件事就断了。

TOOLS · 工具列表（塞进门，给他看）
查日历   查询一组人的空闲时间
订会议   创建会议并返回链接
发群消息 把一段话发到指定的群
建文档   新建一份云文档      ← 新加一行
TOOL_HANDLERS · 分发表（留在门外，给手用）
"查日历"   → calendar.query()
"订会议"   → meeting.create()
"发群消息" → im.send()
"建文档"   → doc.create()     ← 新加一行

纸条上写着工具名，门外按名字在分发表里找到对应的那只手去做。

真实产品里的工具说明，常常带着一串“不要这样做”。每一条背后，几乎都是一次翻车。

术语dispatch map（name → handler）· is_error 回灌
  • （2 分钟）三条经验。
  • 第一条是架构上的好处：加工具不改循环。工具分两半：TOOLS 是说明书列表，塞进门给模型看；TOOL_HANDLERS 是分发表，“工具名 → 处理函数”，留在门外。模型在纸条上写名字，门外按名字查表、调用对应函数。加一个能力，两边各加一行。
  • 第二条给产品和运营：说明书就是 prompt。“什么时候用”这一栏最常被漏写，也最影响选对。
  • 第三条给开发：工具出错不要抛异常中断循环，把错误写成 tool_result 递回去，模型会自己改道。
第一章 · 小结进门出门柜子

博士生只负责“说”，
动手的永远是门外的人。

因为他碰不到任何东西，门外的人才有机会在动手之前检查一下。这条分界线，就是后面所有权限和安全设计的落点。

换个角度看这个循环

Agent Loop 是一套实践论：观察现象 → 提出假设 → 动手实践 → 再观察结果，循环往复，直到任务完成。
Harness 是让这套实践论跑起来的脚手架。

  • （1 分钟）第一章收一句话。

记忆的四个环节：提、存、改、取

谁决定：模型（语义判断）

谁执行：门外（落盘）· 真实产品里几种都有
  • 一个文件全文：如 CLAUDE.md，每次全部带上

  • 索引 + 主题文件：如 Claude Code 的 MEMORY.md，索引常驻，全文按需读
